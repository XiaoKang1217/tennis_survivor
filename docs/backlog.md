### 用户身份与每日赛程竞猜

目标：

- 提高用户留存和每日回访。
- 支持用户用低摩擦方式建立身份。
- 新增每日赛程竞猜模块：选取当日部分比赛，让用户预测胜者；比赛结束后按猜对场数排名。
- 用户可查看总参与人数、个人成绩、排行榜和他人填写明细。

关键设计问题：

- 现有静态 GitHub Pages 不能单独提供可靠注册登录和写入能力，需要引入 Supabase、Firebase、Clerk、Cloudflare Workers + KV/D1 等后端能力，或先做极简身份。
- 如果采用极简身份，例如本地昵称 + 浏览器 token，体验轻但无法可靠防作弊、跨设备和找回账号。
- 如果采用真实登录，建议优先评估 Supabase Auth + Postgres/RLS，兼顾身份、数据写入、排行榜查询和后续点赞/反馈功能。
- 竞猜必须有截止时间，通常应在每场比赛开赛前锁定；是否允许用户提前查看他人选择需要明确，避免跟单影响公平性。
- 需要确认每日赛程来源、赛程更新时间、退赛/赛程取消/延期/中途退赛的结算规则。
- 截止提交不能依赖 GitHub Actions 的半小时更新频率，也不能只靠前端倒计时；必须由后端/数据库按 `lock_at` 强制拒绝超时提交。
- 如果采用“当天第一场比赛前统一截止”，不一定要实时读取比赛进度，但必须提前拿到当日赛程和第一场计划开赛时间，并明确赛程临时变动时是否自动延后或保持原截止时间。

候选实现阶段：

- P0：设计身份方案、数据模型、竞猜规则和 UI 流程。
- P1：只支持昵称/轻身份，验证用户是否愿意每天参与。
- P2：接入真实登录和后端存储，支持跨设备、历史成绩、总榜。
- P3：加入赛季积分、连续参与、徽章或分享卡等留存机制。

Supabase 评估备注：

- 以当前约百人级每日访问量估算，Supabase Free Plan 通常足够支持第一版验证；正式采用前仍需按当时官方价格复核。
- 免费额度重点关注 MAU、数据库大小、流量和项目休眠/可用性限制。
- 开发复杂度中等，主要难点不在登录按钮，而在竞猜截止、结算、防刷、RLS 权限和异常赛程规则。
- 前端应按需加载竞猜模块和 Supabase SDK，避免影响现有静态页面首屏速度。
- 竞猜截止建议用数据库权限或服务端接口按时间校验；赛程抓取和赛果结算可以延迟，但提交锁定必须即时生效。

### 关注用户筛选

目标：

- 在实时选人表新增“关注用户”筛选，方便用户快速查看自己关心的玩家今日选人。
- 支持在用户行或用户详情中关注/取消关注某个用户。
- 关注后可与现有“全部 / 仅存活 / 今日已填”等筛选配合使用。
- 仅在用户尝试关注某位玩家时触发注册/登录；其他现有功能继续免登录使用。
- 已关注用户用黄色星星标识。

候选方案：

- 用户已决定第一版开发注册/登录系统，并将关注关系保存到后端，避免换设备/清缓存丢失。
- 推荐使用 Supabase Auth + Postgres/RLS：Auth 负责注册登录，Postgres 保存关注关系，RLS 控制用户只能写自己的关注列表。
- 可以保留未登录状态下的“关注用户”筛选按钮；点击时提示登录后查看关注列表。

实现注意：

- 关注关系应保存稳定的 `user_id`，显示层仍使用 `username`。
- 当前筛选为空时应显示清晰空状态，例如提示用户先在实时选人表关注玩家。
- 不上传关注关系到 GA4，最多记录使用了“关注用户”筛选这一类匿名事件。
- 注册/登录弹窗应只在用户主动点击关注、查看关注筛选或账号入口时出现，不干扰普通浏览。
- 关注表至少包含登录用户 ID、被关注的幸存者玩家 `user_id`、创建时间；可选记录来源 tour，但匹配关注状态不按 ATP/WTA 拆分。
- 已确认关注不区分 ATP/WTA：同一个幸存者玩家账号被关注后，在 ATP/WTA 数据里出现时都标黄。
- 第一版登录使用用户自定义昵称 + 密码；昵称必填、可包含中英文和特殊字符、不可重复。

当前实现：

- 已新增前端账号弹窗、星标关注、关注用户筛选和 Supabase 懒加载代码。
- 已新增 `docs/supabase-auth-following.md`，记录 Supabase Auth、Postgres、RLS 和验证清单。
- 已填入 Supabase URL / publishable key。
- Supabase Email provider 已开启，Confirm email 已关闭。
- Supabase SQL editor 已执行建表和 RLS 脚本。
- 已通过本地真实链路验证：注册、重复昵称拦截、登录、关注、刷新后保持关注、关注用户筛选、取消关注。
- 已扩展到积分构成和用户偏好：同一个 `user_id` 在实时选人、积分构成、用户偏好中共用星标状态和“关注用户”筛选。

### 签表挑战观察室

目标：

- 在炉网新增一个围绕 live-tennis 原站“签表挑战”的轻量模块，先做公开数据观察和娱乐分析，不承接提交签表。
- 帮用户快速看到当前开放挑战、截止时间、预测分布、共识冠军、冷门路线和外链入口。
- 保持炉网的“看信息、找乐子、辅助决策”定位，不替代原站登录和填表流程。

已调研：

- 原站比分/赛程页标题和菜单包含“签表挑战”。
- 当前菜单接口：`https://www.live-tennis.cn/zh/dc/menu`，可读到当前开放挑战，例如 2026 法网 ATP/WTA。
- 赛历入口：`https://www.live-tennis.cn/zh/dc/calendar/2026`。
- 赛事入口样例：`https://www.live-tennis.cn/zh/dc/RG/2026/MS`。
- 预测分布入口样例：`https://www.live-tennis.cn/zh/dc/RG/2026/MS/distribution`，公开展示冠军、半区、1/4 区、1/8 区和决赛对阵分布。
- 排行榜入口样例：`https://www.live-tennis.cn/zh/dc/RG/2026/MS/rank`，榜单数据通过 CSRF 保护的 POST query 加载，后续如需抓取要专门验证 cookie/token 流程。
- 规则页：`https://www.live-tennis.cn/zh/help/rule/dc`。规则要点是大满贯和 ATP/WTA 1000 赛期间进行，用户登录后提交整张签表；大满贯截止为正赛首日最早开赛时间；1000 赛截止为资格赛落位后次日最早开赛时间；计分按晋级轮次累加，大满贯和 96 签 1000 满分 520，56 签 1000 满分 235。

第一版建议：

- 模块名：`签表挑战观察室`。
- 数据源先只用 `dc/menu`、赛事页和 `distribution` 页面，避开需要登录或 CSRF POST 的提交/榜单接口。
- 展示“当前挑战卡片”：赛事、ATP/WTA、截止时间、原站填表链接、预测分布链接。
- 展示“民意天气”：冠军共识、决赛最大众对阵、四个 1/4 区最大热门、争议度最高区块。
- 展示“反共识雷达”：找出热门占比很低但进入后段轮次的人，作为娱乐向冷门提醒。
- 增加一键跳转原站填表，明确“提交签表请回原站完成”。

候选后续：

- 如果排行榜 query 能稳定抓取，再做“炉网用户找人/排名快查”和“签表挑战即时榜单”。
- 如果未来接入登录/后端，再考虑用户在炉网保存自己的签表草稿、和大众分布比较、生成分享卡。
- 可把签表挑战结果与幸存者数据联动，做“幸存者玩家在签表挑战里是否更偏热门/更保守”的趣味分析；这需要用户身份映射，先不做。
