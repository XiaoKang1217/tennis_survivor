# Backlog

## 近期优先级

### GA4 PV/UV 和模块访问统计

目标：

- 了解每天访问量。
- 了解用户主要看哪些模块。
- 为后续功能优先级提供依据。

状态：

- 前端接入已完成。
- Measurement ID 已填写，发布后即可开始发送。

### 单文件前端拆分

目标：

- 降低 `index.html` 维护成本。
- 将渲染、筛选、排序、数据加载、埋点拆开。

风险：

- 当前站点是纯静态单文件，拆分时要保证 GitHub Pages 路径和缓存不出问题。

### 数据懒加载

目标：

- 首屏更快。
- 用户进入某个模块时再加载对应 JSON。

候选拆分：

- 实时选人：`current.json`
- 积分构成：`breakdown.json`
- 历史/偏好/航班：`history.json`

### 更完整的测试

目标：

- 覆盖积分规则、状态分类、历史惨案生成、航班回退规则。

已有：

- 四大满贯强制 0 分规则测试。

### 点赞/反馈功能

目标：

- 支持用户给惨案、航班、功能建议点赞。

技术方向：

- 如果只是本地假按钮，不需要后端。
- 如果点赞数要真实保存，需要 Supabase、Firebase、Cloudflare Workers 或 Google Apps Script。

建议：

- 第一版优先考虑 Supabase 或 Cloudflare Workers。

## 中期方向

- 后台化赛事规则配置，减少年份和赛事硬编码。
- 自动识别新赛事类型和积分规则。
- 历史惨案文案风格分层：辛辣、扎心、冷幽默、克制版。
- 用户反馈入口。
- 管理员手动触发数据更新。
- 异常数据报警，例如当天 current 数据为空、活跃赛事误判、Actions 连续失败。

## 长期维护方向

- 明确数据模型。
- 建立 release checklist。
- 将核心业务规则从页面渲染中剥离。
- 保持静态站的低成本优势，只在需要写入数据时引入后端能力。
