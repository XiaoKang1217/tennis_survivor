# 炉网实时比分服务

这个服务是浏览器与 API Tennis 之间的唯一数据入口。API key 只保存在服务器的 `/etc/luwang-live-score.env`，不会进入 Git、前端或浏览器网络请求。

## 轮询规则

- API Tennis 赛程候选缓存 6 小时；ATP/WTA 官方赛程每 5 分钟复核一次。ATP OOP 尚未发布时保留候选赛程并持续重试，不会用空结果覆盖候选。
- 赛前赔率通过 API Tennis `get_odds` 按当天及次日批量获取，每小时刷新并按比赛 ID 合并；优先展示 bet365，缺失时依次回退到 1xBet、Betway、bwin 或首个完整盘口。
- 没有进入开赛观察窗口时，不请求 `get_livescore`。
- 预计开赛前 15 分钟进入观察窗口；尚未确认有进行中比赛时，每 60 秒请求一次。
- API 确认至少一场比赛进行中后，固定每 8 秒请求一次，并通过 SSE 推送给所有在线用户。
- 所有进行中比赛结束或从 `get_livescore` 消失后，退出 8 秒轮询；当天仍有待开始比赛时，在下一场观察窗口恢复 60 秒检查。
- 赛程归属按赛事所在地时区的官方日历日判断；比赛时间只在展示时换算成北京时间。官方赛程日的比赛若落在北京时间次日，仍只归原官方赛程日并标记 `+1`，不会按固定凌晨分界重复归档。
- 北京时间进入新的一天后立即预抓并缓存新赛程，日期选择器可提前查看；上一官方赛程日全部比赛结束后，才自动把默认日期切换到新的赛程日。
- 从 2026-07-22 起永久保存每个赛程日的数据快照；前端日期选择器只展示最近 5 个赛程日，展示窗口滚动不会删除历史快照。
- API Tennis 的 `get_fixtures` / `get_livescore` 是实时生产主数据源。
- WTA 官方公开接口按官方日历日逐场校验对阵、球场、场地类型、状态和赛果；完整官方清单会剔除同站同日无法匹配的 API 脏记录，并补回 API 遗漏的正式比赛。
- ATP 本地年度官方赛历只保存正赛赛事 ID、标准赛事名、日期、城市、国家、级别、场地类型和时区；增加新年度时只需增加 `data/atp-tournaments-YYYY.json`，无需修改程序。
- 每个有效赛程日按正赛 ATP ID 下载 ATP 官方 `op.pdf`，逐场按“完整双方球员＋单/双打”与 `get_fixtures` 候选匹配。OOP 决定官方赛程日、对阵、比赛顺序、时间和具体球场，页头决定城市、国家和场地类型，本地赛历负责交叉核验。赛事 URL 的 slug 不参与身份判定。
- ATP OOP 同一地址可能每天覆盖，因此每次成功解析都以“正赛 ATP ID＋官方赛程日”保存当前快照，并按 PDF SHA-256 永久保留不同修订。PDF 尚未发布、日期不符、页头元数据冲突或任一正式比赛行解析失败时，继续使用同日已保存快照；没有快照时保留 fixtures 候选并等待重试。
- OOP 的 `A or B`、Qualifier、Lucky Loser、Alternate、Winner 等待定项支持候选匹配；一旦 fixtures 已给出确定球员，不会被占位文字覆盖。
- 生产数据链完全不请求竞品站点。中文球员名只来自仓库内经过人工复核的球员翻译表；本地化代码没有修改赛事归属、日期、时间、场地类型、球场、状态、赛果、排序或增删的权限。
- API 或官方来源一旦确认完赛，会同时写入持久 event ID 锁、同 ID 前态锁和“官方赛程日＋单双打＋完整双方球员”逻辑指纹锁；后续响应不能把它降级为进行中或未开赛。
- 不再根据 6500、7300、7800 等本地请求计数改变刷新速度或主动停止。
- 所有浏览器共享服务端的一次请求和缓存，访问人数不会成倍消耗上游额度。

## 数据生产边界

1. `get_fixtures` 创建候选赛程基线，并提供 API event ID、赔率关联字段及其他接口字段。
2. 候选赛事按赛事名、城市和官方日期匹配本地 ATP 年度赛历；赛历提供正赛 ATP ID、标准名及 ATP 250/500/1000 等赛事级别。
3. ATP OOP / WTA 官方日程按“巡回赛＋官方赛程日＋完整双方球员＋单双打”逐场核对；完整官方清单决定赛程是否存在、赛事归属、球场、场地和顺序。
4. `get_livescore` 只能覆盖白名单比赛的状态、盘分、局内分、发球方和最后一分，不得新增比赛或修改日期、赛事、球场、场地和球员。
5. 完赛锁位于实时覆盖之前；event ID、前态和逻辑指纹三层锁任一确认完赛，后续 fixtures 或 livescore 均不能降级。
6. 中文本地化只替换球员显示名；赛事事实字段在进入本地化层之前已经冻结。
7. 可选的第二实时源（见下）位于 `get_livescore` 之前，只能补 `get_livescore` 未返回的比赛，权限严格小于第 4 条。

## 可选：第二实时比分源（默认关闭）

`get_livescore` 偶尔会漏掉官方赛程上确实在打的比赛，或在一次请求失败后让整块看板停住。可以配置一个**补充**实时源来填这些空档。

- **默认完全关闭。** 不设 `LIVETENNISAPI_KEY` 时不新增任何请求、任何依赖，快照与现在逐字节一致。
- 启用后 API Tennis 仍是默认主源：第二源在主源覆盖**之前**应用，因此 `get_livescore` 报过的比赛一律以主源为准，第二源只填它没报的那些。
- 第二源的权限比第 4 条更窄，只允许把一场**已经在官方赛程里**的比赛补成进行中，并提供盘分、局内分和发球方：
  - 不新增比赛。匹配不到唯一一场官方赛程比赛的行直接丢弃。
  - 不写任何终态。只发出 `live`，因此它无法把比赛锁成完赛、取消或隐藏；完赛判定仍然只属于 `get_fixtures`、ATP/WTA 官方来源和现有三层完赛锁。
  - 不改身份字段。每条更新都是官方赛程那场比赛的副本，只替换比分字段，赛事、日期、时间、球场、场地和球员在结构上就改不动。
  - 不编造比分。盘分只来自对方确实返回的整数局分；完赛比赛可能带空的 `games` 数组，此时不补分，宁可不出。
  - 不跨源桥接 ID。匹配方式是同一赛程日内“完整双方球员”精确归一化配对，任一侧出现歧义即丢弃，且不会把对方的 event ID 写进赛程。
  - 只处理单打，双打留给主源。
- 配置：

```sh
LIVETENNISAPI_KEY=<key>
# LIVETENNISAPI_BASE 可选，默认 https://api.livetennisapi.com/api/public/v1
```

  每个观察周期只多一次 `GET /matches?status=live`（免费档即可），沿用现有的观察窗口节流，因此不在观察窗口内不产生任何请求；返回 429 时退避一分钟。`/health` 增加 `secondaryLiveConfigured` 字段，`/api/v1/live/*` 快照的 `sourcePolicy.live` 会如实标明该源是否启用。

  披露：livetennisapi.com 由本 PR 作者运营。它在这里是可选的补充项，不是替代 API Tennis 的建议。

## 本地启动

复制 `.env.example` 中的变量到安全的进程环境后运行：

```sh
npm test
npm start
```

前端默认请求同源 `/api`。本地生产同构预览可通过 `?live-api=http://127.0.0.1:8787` 指向 SSH 隧道后的服务器服务。

## 生产部署

1. 服务代码安装到 `/opt/luwang-live-score/current`。
2. 环境文件安装到 `/etc/luwang-live-score.env`，权限 `0600`。
3. 缓存目录使用 `/var/lib/luwang-live-score`。
4. systemd 使用 `deploy/luwang-live-score.service`。
5. Nginx 使用 `live-api.tennisapi.online` 并配置 HTTPS 证书。

生产前端设置：

```html
<script>window.LUWANG_LIVE_API_BASE='https://live-api.tennisapi.online';</script>
```
